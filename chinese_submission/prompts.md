# 使用的提示

## 总结提示

**角色：** 你是一名严谨的 NLP 分析员，负责为学生事务办公室管理者准备简明报告。

**任务：** 总结输入数据中的校园班车追踪应用反馈，识别总体趋势、主要主题、用户影响、正面反馈、高优先级风险、缺失或模糊信息，以及可执行的后续步骤。

**背景：** 数据集包含来自应用评论、客服邮件、调查回复和聊天记录的 12 条原始反馈。部分记录包含多个问题、正负混合评价或用户猜测。

**输入数据：** 使用下方“原始数据集”中的 R01–R12。

**输出格式：** 严格使用下列 Markdown 结构；“主要主题”表格至少三行，每个主题、正面要点和风险都必须引用记录 ID。

```text
# 校园班车应用反馈摘要(Campus Shuttle App Feedback Summary)
## 1. 一句话概述 (One-Sentence Overview)
## 2. 主要主题 (Top Themes)
| 主题 | 证据ID | 用户影响 | 建议行动 |
|--- |--- |--- |---|
## 3. 正面反馈(Positive Feedback)
## 4. 高优先级风险 (High-Priority Risks)
## 5. 缺失或模糊信息 (Missing or Ambiguous Information)
## 6. 建议的后续步骤 (Recommended Next Steps)
```

**规则：**
- 只能使用原始记录明确提供的信息。
- 不得虚构姓名、原因、技术解释、日期、政策或解决方案。
- 用户的猜测只能标为猜测，不能写成已确认原因。
- 每项实质性主张必须由一个或多个记录 ID 支持。
- 明确说明不确定性和缺失信息。
- 在缺乏证据时建议“调查”或“核实”，不得断言具体修复方案。
- 表述简洁、面向管理者，并能在两分钟内浏览完毕。

## 提取提示

**角色：** 你是一名严谨的 NLP 信息提取分析员。

**任务：** 将每条输入记录转换为一个结构化 JSON 对象，并生成数据集层面的洞察。

**背景：** 数据描述学生对试点校园班车追踪应用的反馈。一条记录可能包含多个问题；请选择证据支持的主要问题类别。紧急程度统一按以下规则判断：出现安全、无障碍、付款或服务无法使用等明确后果时为“高”；未解决的功能或可读性问题为“中”；未说明即时伤害的增强请求为“低”。

**输入数据：** 使用下方“原始数据集”中的 R01–R12。

**输出格式：** 只返回一个可解析的 JSON 对象，顶层键必须为 `records` 和 `dataset_level_insights`。完整包含 12 条记录。每条记录按顺序包含：`id`、`date`、`source`、`issue_category`、`sentiment`、`urgency`、`user_need`、`requested_action`、`evidence_quote`、`needs_follow_up`、`missing_information`。数据集洞察包含：`most_common_issue_categories`、`highest_priority_record_ids`、`overall_sentiment`。

**受控词汇：**
- `source`：`应用评论`、`客服邮件`、`调查反馈`、`聊天记录`
- `issue_category`：`时效准确性`、`退款问题`、`可访问性`、`应用程序漏洞`、`安全问题`、`隐私问题`、`功能需求`、`正面反馈`、`不明确`
- `sentiment`：`正面`、`中性`、`负面`、`不明确`
- `urgency`：`低`、`中`、`高`
- `overall_sentiment`：`正面`、`中性`、`负面`、`不明确`

**规则：**
- 仅使用输入信息；绝不虚构缺失细节或技术原因。
- 每条记录复制一段简短、准确的原文作为证据。
- `requested_action` 等没有依据的值使用 JSON 的 `null`。
- 将未解决或缺失的细节列入 `missing_information`；仅在没有重要缺失项时使用空数组。
- 未解决的问题或请求将 `needs_follow_up` 设为 true；仅纯正面反馈可设为 false。
- 不得把 R08 对“路线名称没有翻译”的猜测写成事实。
- 所有键和字符串使用双引号；不得添加注释、尾随逗号或 Markdown 代码围栏。
- 返回前检查：JSON 可解析，R01–R12 各出现一次，标签均来自受控词汇，所有主张有原文证据。
